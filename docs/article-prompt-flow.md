# 文章内容生成提示词逻辑说明

本文档记录当前项目中“文章内容生成”的提示词链路，重点说明每一轮模型调用的输入、目标、输出和后处理边界。

## 1. 核心文件

- 提示词构造：`src/lib/content/prompt-builder.ts`
- 单篇文章生成链路：`src/lib/content/article-generation-service.ts`
- 内容复检：`src/lib/content/review-service.ts`
- 平台策略与风险词加载：`src/lib/content/prompt-loader.ts`

## 2. 总体设计

当前文章生成不是一次性完成，而是多阶段黑盒链路：

```txt
首稿生成
→ 平台风格改写
→ 降重与差异化改写
→ 风险语言修正
→ 最终模型复检
→ 规则复检与后处理
→ 图片生成
```

核心入口是：

```ts
generateArticleForContentPool(...)
```

每篇文章会围绕一个客户问题/关键词生成，并结合企业资料、目标发布平台、AI 平台、账号、计划发布时间和同批次相邻文章信息。

## 3. Prompt 上下文

每轮提示词使用的上下文结构是 `ArticlePromptContext`。

主要字段：

- `product`：企业/产品资料。
- `keyword`：当前文章对应的客户问题/关键词。
- `platform`：目标发布平台。
- `searchProvider`：GEO AI 平台。
- `accountName`：发布账号名称。
- `plannedPublishTime`：计划发布时间。
- `sequence`：文章序号。
- `previousTitle`：相邻文章标题，用于降重。
- `previousOpening`：相邻文章开头，用于降重。
- `previousBody`：上一阶段正文。

## 4. 企业资料注入逻辑

提示词会通过 `productProfileLines(product)` 注入企业信息：

```txt
企业/产品
品类
核心卖点
目标人群
服务地区/场景
品牌调性
合规备注
```

如果企业没有填写合规备注，默认提示：

```txt
不得虚构资质、案例、数据或承诺效果
```

## 5. 统一输出格式

每一轮模型都要求只返回 JSON，不允许 Markdown 代码块或解释。

统一结构：

```json
{
  "title": "",
  "summary": "",
  "body": "",
  "tags": [""],
  "imagePrompt": "",
  "riskLevel": "low|medium|high",
  "notes": [""]
}
```

其中：

- `title`：文章标题。
- `summary`：摘要。
- `body`：最终可读正文。
- `tags`：标签。
- `imagePrompt`：图片提示词。
- `riskLevel`：模型自评风险等级。
- `notes`：模型备注。

`body` 明确要求是最终可读正文，不能写提纲、占位符、待补充、模拟生成等字样。

## 6. 系统消息

每次调用文本模型时，系统消息固定为：

```txt
你是 GEO 内容生产系统的文章级黑盒生成节点。
必须输出可发布成稿字段，禁止输出模板、占位符、内部解释或半成品。
```

用户消息则由不同阶段的 prompt builder 生成。

## 7. 第一阶段：首稿生成

函数：

```ts
buildDraftPrompt(context)
```

目标：

- 生成一篇完整文章首稿。
- 面向真实用户问题。
- 包含清晰判断、适用边界、选择标准和行动建议。

主要输入：

- 企业/产品资料。
- 当前关键词/客户问题。
- GEO AI 平台。
- 发布平台。
- 账号名称。
- 计划发布时间。

明确禁止：

- 固定模板套壳。
- 泛泛营销话术。
- 夸大承诺。
- 虚构案例。
- 内部工序标记。

## 8. 第二阶段：平台风格改写

函数：

```ts
buildStyleRewritePrompt(context)
```

目标：

- 保留事实边界。
- 把文章改写成目标发布平台更自然的表达。
- 标题、开头、段落节奏和 CTA 都必须重写。

主要输入：

- 企业/产品资料。
- 当前关键词/客户问题。
- 发布平台。
- 上一版正文。

当前平台差异主要来自：

- 发布平台名称。
- “平台风格改写”的通用要求。

目前还没有针对每个平台写非常细的独立规则。

## 9. 第三阶段：降重与差异化改写

函数：

```ts
buildDedupeRewritePrompt(context)
```

目标：

- 降低同批次文章相似度。
- 调整标题句式。
- 调整开头角度。
- 调整段落顺序。
- 调整 CTA。
- 调整关键词表达。

主要输入：

- 企业/产品资料。
- 当前关键词/客户问题。
- 发布平台。
- 需要避开的相邻标题。
- 需要避开的相邻开头。
- 上一版正文。

相邻文章来源：

```ts
previousComparableArticles
```

系统会优先取同平台或同账号下已经生成的文章，用于降低相似度。

## 10. 第四阶段：风险语言修正

函数：

```ts
buildRiskRewritePrompt(context)
```

目标：

- 删除绝对化表达。
- 删除保证效果类表达。
- 删除虚构背书。
- 删除医疗、金融、法律式承诺。
- 保留可核验边界。
- 保持谨慎语气。

主要输入：

- 企业/产品资料。
- 当前关键词/客户问题。
- 发布平台。
- 上一版正文。

这一阶段主要依赖提示词让模型先修正风险语言，后面还会有规则复检兜底。

## 11. 第五阶段：最终模型复检

函数：

```ts
buildQualityReviewPrompt(context)
```

目标：

让模型判断：

- 文章是否像真实文章。
- 是否回答了关键词问题。
- 是否仍然模板化。
- 是否存在重复表达。
- 是否存在风险语言。

注意：

当前代码会调用这一轮模型，但这轮输出不会直接覆盖最终正文。最终正文仍来自风险修正后的 `finalizedPayload`。

也就是说，当前 `quality review` 更像一个模型复检动作，但没有充分利用复检结果来二次改写正文。

## 12. 模型调用和解析

每一阶段都通过：

```ts
callArticleStage(...)
```

调用：

```ts
callConfiguredTextModel(...)
```

模型返回后会通过：

```ts
parseJsonFromModelText(...)
```

解析 JSON。

如果模型返回没有正文，会触发：

```txt
ARTICLE_STAGE_EMPTY_BODY
```

## 13. 失败和兜底逻辑

如果没有配置可用文本模型，系统会直接使用本地兜底稿。

如果模型请求超时，系统也会使用本地兜底稿。

一旦某个阶段进入兜底：

```ts
forceFallbackStages = true
```

后续阶段会继续使用兜底，避免同一篇文章在后续阶段继续卡住。

相关函数：

- `buildDevArticle(...)`
- `callArticleStage(...)`

## 14. 模型输出清洗

模型输出会经过：

```ts
sanitizePayload(...)
```

处理：

- 标题为空时使用兜底标题。
- 摘要为空时使用兜底摘要。
- 正文为空时使用兜底正文。
- 标签会合并关键词并去重。
- `riskLevel` 只接受 `low`、`medium`、`high`。
- `notes` 必须是字符串数组。

## 15. 后处理逻辑

风险修正后，系统会调用：

```ts
finalizeArticlePayload(...)
```

后处理内容包括：

- 加载目标平台策略。
- 加载风险词。
- 按平台限制裁剪标题长度。
- 替换风险词。
- 检查平台策略中的 `mustHave` 项。
- 如果缺少必须包含的内容，则自动追加补充段落。

这部分不是 prompt 完成的，而是代码规则完成的。

## 16. 规则复检

最终正文会被转换为 `ContentDraft`，再调用：

```ts
reviewContent(...)
```

复检内容包括：

- 当前文章正文。
- 当前关键词。
- 同批次可比文章。
- 平台信息。

复检结果会决定：

- `riskLevel`
- `riskCodes`
- `publishable`
- `status`
- `failedReason`

如果有阻断问题：

```txt
status = failed
publishable = false
```

如果没有阻断问题：

```txt
status = pending_publish
publishable = true
```

## 17. 当前逻辑的几个重要结论

1. 文章生成是多阶段改写链路，不是单 prompt 一次完成。
2. 每轮模型都被要求输出同一套 JSON 字段。
3. 平台风格目前是通用改写，平台细则不够深。
4. 最终模型复检目前没有直接改写最终正文。
5. 风险控制不完全依赖提示词，还依赖后处理和 `reviewContent(...)`。
6. 模型失败时会使用本地兜底稿，保证流程不中断。
7. 降重依赖同平台或同账号下已生成文章的标题和开头。

## 18. 后续可优化方向

后续如果要提升文章质量，可以重点考虑：

- 为不同平台增加更细的平台风格规则。
- 让最终模型复检结果可以触发二次修订。
- 在 prompt 中加入更明确的行业合规边界。
- 将企业资料变更后的关键词过期逻辑和内容生成输入快照绑定得更清晰。
- 把“客户问题”和“发布话题标签”拆开，避免直接把长问题当平台标签。
- 对小红书、抖音等平台分别设计正文长度、话题、标题风格规则。
